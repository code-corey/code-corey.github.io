> 锁与同步系列完结后的实战加餐。系列 1~7 篇讲的是 JDK 自带的锁；这篇讲一个工程里自己动手造锁的经典模式——**分片锁（Striped Lock）**，案例来自我真实改造的多语言镜像写模块。

---

## 开头：一次真实的"旧译文覆盖新译文"

背景：官网 CMS 的内容要镜像成英文表和阿拉伯文表（`content` / `content_en` / `content_ar`，三表同主键）。为了不让保存接口等着大模型翻译，改造后保存事务只发一个事件，事务提交后由异步线程池去完成"翻译 + 写镜像"。

上线前推演发现了竞态：运营快速**连续保存同一篇内容两次**，就有两个异步任务先后处理同一条记录——

```
任务1：读到主表第 5 号记录（标题 v1）→ 翻译中……
任务2：读到主表第 5 号记录（标题 v2）→ 翻译完成 → 写入 en/ar 表
任务1：翻译完成 → 写入 en/ar 表        ← 旧译文 v1 把新译文 v2 盖掉了！
```

解法很直觉：**同一条记录的镜像写必须串行**。但"记录"是数据库里的行，理论上有无限多条——锁从哪来？

---

## 一、把需求说精确

把上面的直觉翻译成三条硬需求：

| # | 需求 | 性质 |
|---|------|------|
| 1 | 同一条记录（表名 + 主键）必须互斥 | **正确性**，一票否决 |
| 2 | 不同记录尽量并行 | 性能期望 |
| 3 | 锁对象内存可控、无需清理 | 工程约束 |

注意需求 1 和 2 的地位不平等：**1 必须百分百成立，2 尽力而为**。记住这个不对等，后面所有设计都是围绕它做取舍。

---

## 二、直觉方案逐个翻车

### 方案一：`synchronized (pkid)` —— 锁主键对象

最直觉的写法，也是死得最惨的。Java 的 `synchronized` 锁的是**对象引用**（监视器），跟对象的**值**毫无关系。而"pkid 是唯一的"说的是**值的唯一**——两码事：

```java
Long a = 5L;
Long b = 5L;
System.out.println(a == b);   // true！-128~127 落在 JVM 的 Long 缓存池

Long x = 10507L;              // 第一次保存请求带来的主键
Long y = 10507L;              // 第二次保存请求带来的主键（值完全相同）
System.out.println(x == y);        // false！超出缓存范围，各自装箱
System.out.println(x.equals(y));   // true —— 值唯一，但引用是两个
```

这是 JLS §5.1.7 规定的确定性行为：装箱缓存只保证 `-128 ~ 127`。

致命之处在于：**我们要防的恰恰是两次独立请求**，每次请求的主键都是从各自的报文里装箱出来的**新 Long 对象**——

```java
synchronized (pkidFromRequest1) { ... }   // 锁对象 A
synchronized (pkidFromRequest2) { ... }   // 锁对象 B，和 A 毫无关系
```

两把不同的锁 = 完全没有互斥，而且**编译不报错、运行不报错、单线程测试全绿**——锁静默失效，比崩溃危险得多。这是《Effective Java》里的经典告诫：永远不要用共享的装箱类型做锁。

反过来更糟：假如主键恰好 ≤ 127，锁的是 JVM 全局共享的**缓存对象**——menu 表的 5 号和 news 表的 5 号锁在一起，还可能和进程里任何其他锁同一个 `Long` 的代码互相干扰。

### 方案二：锁查出来的行对象

`synchronized (row)`？`selectById` 每次都返回**新对象**，两次查询拿到两个不同的监视器，同样锁不住。

### 方案三：`ConcurrentHashMap<key, Object>` 动态锁表

为每个键造一把锁存进 map——方向对了（这就是"规范锁 canonical lock"思想），但键随记录无限增长，还得回答"这把锁什么时候能删"：引用计数？弱引用？过期清理？复杂度陡增。

### 方案四：`"menu:5".intern()` 锁字符串

intern 池保证同值同对象，能工作，但字符串池是全局命名空间，行为依赖池实现，公认反模式。

## 三、分片锁的思想：不造无限把锁，造 64 把

换个角度想需求。我们其实**不需要**"每条记录一把锁"，只需要"**同一条记录永远抢到同一把锁**"。

于是做法是：预先造 **64 把固定锁**，用哈希把无限多个 (表名, 主键) **分配**到这 64 把锁上。

生活化类比：洗车行只有 64 个工位，调度规则是"按车牌号哈希分配工位"。同一辆车今天来明天来，永远被分到同一个工位（确定性）；两辆不同的车可能被分到同一个工位（碰撞），那就排个队——**只是慢一点，不会出错**。

对照三条需求验收：

| 需求 | 满足情况 |
|------|---------|
| 同记录互斥 | ✅ 哈希是确定性函数：同键每次算出同一个锁 |
| 不同记录并行 | ✅ 大概率分到不同锁；偶尔碰撞只是短暂排队 |
| 内存可控 | ✅ 恒定 64 个对象，几 KB，永不清理 |

碰撞的本质：**用并行度换内存**。64 把锁守无限条数据，靠的就是接受"无害的碰撞"。

## 四、15 行实现，逐行拆

```java
private static final int STRIPE_COUNT = 64;

private static final Object[] STRIPES = buildStripes();

private static Object[] buildStripes() {
    Object[] stripes = new Object[STRIPE_COUNT];
    for (int i = 0; i < STRIPE_COUNT; i++) {
        stripes[i] = new Object();   // 纯粹当监视器用，无任何数据
    }
    return stripes;
}

private static Object stripe(String tableName, Long pkid) {
    int hash = 31 * tableName.hashCode() + Long.hashCode(pkid);
    return STRIPES[hash & (STRIPE_COUNT - 1)];
}
```

就这么多。玄机全在 `stripe()` 的两行里。

### 第一行：把 (表名, 主键) 揉成一个指纹

```java
int hash = 31 * tableName.hashCode() + Long.hashCode(pkid);
```

拿真实数字走一遍 `(menu, 5)`（以下输出都是本机实跑）：

```
"menu".hashCode()  = 3347807
Long.hashCode(5L)  = 5
31 * 3347807 + 5   = 103782022
```

`31 * a + b` 是经典散列合并公式（`Objects.hash(a, b)` 和 record 自动生成的 `hashCode` 都是它）：乘 31 把前一个数的比特"错开"再叠加后一个，让不同组合尽量得到不同指纹。

为什么必须带上表名？menu 表的 5 号和 news 表的 5 号是**两条不同记录**，只用主键做哈希会让它们永远锁在一起——不损正确性，但白白排队。

### 第二行：指纹撒到 64 把锁上

```java
return STRIPES[hash & (STRIPE_COUNT - 1)];
```

`64 - 1 = 63` = 二进制 `111111`。`hash & 63` 只保留低 6 位，结果必然落在 `0 ~ 63`，正好当数组下标。

上面 `103782022 & 63`：二进制末 6 位是 `000110` = **6** → `STRIPES[6]`。

用 `&` 而不是 `% 64` 有两个原因：

1. **负数安全**：Java 的 `%` 对负数返回负数（`-5 % 64 == -5`），而 `hashCode()` 完全可能为负 → `STRIPES[-5]` 直接越界。`& 63` 只取低 6 位，符号位天然丢弃，任何 int 进来结果都是非负（`-7 & 63 == 57`）。
2. **快**：`&` 是单条 CPU 指令——这正是 `HashMap` 定位数组的同款手法：`(n - 1) & hash`。

**前提**：`STRIPE_COUNT` 必须是 2 的幂，`N - 1` 的二进制才是全 1 掩码。这就是常量选 64 而不是 60 / 100 的原因。

### 实跑验证：谁和谁共享同一把锁

```java
(menu,5)  -> lock[6]
(menu,5)  -> lock[6]   // 同一条记录算两次，必然同锁 ← 串行性由此保证
(menu,6)  -> lock[7]
(menu,99) -> lock[36]
(news,5)  -> lock[18]  // 同号不同表 → 不同锁
(news,2)  -> lock[15]
(menu,-5) -> lock[5]   // 负主键也不炸
```

### 使用姿势

```java
synchronized (stripe(tableInfo.getTableName(), pkid)) {
    // 锁内重读主表 → 拿到的必然是最新已提交数据
    // 翻译、写镜像……
}
```

哈希是确定性函数：相同 `(menu, 5)` 无论哪个线程、何时调用，永远落到 `STRIPES[6]`，抢的是**同一把**监视器——互斥成立。

### 锁内做重活，行不行？

我的场景里锁内要等大模型翻译（秒级）。看似奢侈，但想清楚锁的粒度：锁的是"**这一条记录的写权**"，等锁的只有同一条记录的后续任务——而"让它们排队"正是需求本身。64 把锁 × 独立线程池，全局吞吐不受影响。

真正要避免的是**锁内再做需要其他分片锁的事**（锁叠加），那是死锁的温床。

## 五、Guava Striped：现成的轮子

这个模式太常用，Guava 直接提供了 `com.google.common.util.concurrent.Striped`：

```java
private static final Striped<Lock> STRIPES = Striped.lock(64);

Lock lock = STRIPES.get(tableName + ':' + pkid);
lock.lock();
try {
    // 临界区（return 提前退出也没关系，finally 保证解锁）
} finally {
    lock.unlock();
}
```

生产代码里我把手写版换成了它，净删约 20 行。几个变体按需选：

| 工厂方法 | 特点 |
|----------|------|
| `Striped.lock(n)` | 预创建 n 把 `ReentrantLock`（强引用），最常用 |
| `Striped.lazyWeakLock(n)` | 惰性创建 + 弱引用，锁可被 GC，适合超大 n |
| `Striped.readWriteLock(n)` / `Semaphore(n)` | 同样思想分片读写锁 / 信号量 |

值不值得引依赖？我的判断标准：**项目里已有 Guava** → 毫不犹豫用它；**就为这一个类引依赖** → 15 行手写也不丢人。我的项目里本地仓库本来就有 Guava，所以换了。

## 六、这个思想无处不在

分片锁不是孤立技巧，它是"**固定资源池 + 哈希分配**"这一通用模式在互斥场景的投影：

- **JDK 7 的 ConcurrentHashMap**：`Segment[]` 分段锁，每段一把 ReentrantLock——分片锁最著名的应用（JDK 8 换成了 CAS + 锁单桶头节点，粒度更细的另一条路线）；
- **LongAdder**：热点计数不争一个 `base`，分散到 `Cell[]` 数组上，汇总再求和——把"争一把锁"改成"分片记各自账"；
- **数据库 / 缓存分片**：一致性哈希把 key 分到有限节点——同样的哈希分配，粒度换成了机器。

共同点一句话：**键空间无限，资源有限，用确定性哈希做映射，用"接受碰撞"换"免维护"**。

## 小结

| 决策点 | 结论 |
|--------|------|
| 为什么不 `synchronized(pkid)` | 锁认引用不认值；两次请求的 Long 是两个对象，锁静默失效 |
| 为什么不动态锁表 | 键无限增长 + 清理难题 |
| 正确性靠什么 | 哈希的**确定性**：同键必同锁 |
| 碰撞怎么办 | 接受：只损并行度，不损正确性 |
| 分片数怎么选 | 2 的幂；越大并行越好、内存越多，小规模写入 64 足够 |
| 手写还是 Guava | 已有 Guava 用 `Striped.lock(n)`；否则 15 行手写不丢人 |

最后留个心法：下次发现"要给无限多的东西加锁"时，先问自己——**我要的到底是"每样东西一把锁"，还是"同一样东西永远同一把锁"？** 大多数时候是后者，那就只需要 64 把锁。
