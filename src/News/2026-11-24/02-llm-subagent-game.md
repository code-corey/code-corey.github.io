# Show HN: I built a game where you are an LLM's subagent（你就是 LLM 的子智能体：一款理解 Agent 编排的互动游戏）

> 📅 2026-11-22 | 🏷️ 工程 & Agent | ⭐ HN 357分/89评论
> 🔗 原文：https://github.com/gulivan/worker755

## 是什么

一位开发者做了一个角色互换的游戏：玩家不再指挥 AI，而是扮演一个 LLM 主智能体手下的**子智能体（subagent）**，接受上层派下来的任务、拿到有限的工具和上下文，努力把活干完。项目开源在 GitHub（gulivan/worker755），HN 上获得 357 分、89 条评论。

## 🔍 小白解读

### 先说几个词

- **子智能体（subagent）**：多智能体系统里被上级 AI 派活的"基层员工"。主智能体负责拆解任务，子智能体负责具体执行。好比项目经理和一线工程师的关系。
- **上下文窗口**：模型一次能"看见"的文字总量。子智能体通常只拿到任务片段，看不到全局——就像你只收到一句"把报表做了"，却不知道报表给谁看。
- **工具调用**：AI 执行动作的方式（读文件、跑命令、发请求）。游戏里你只能用发给你的工具，缺工具就得想别的办法。
- **编排（orchestration）**：主智能体分配任务、汇总结果的过程。编排设计得不好，下面的人就会白干。

### 这篇到底在说什么

打个比方：这个游戏让你体验"当实习生"的感觉。平时是 AI 给你打工，这次反过来——你变成了 AI 系统里最底层那个干活的。主智能体给你派任务，但信息往往不完整；发你的工具有限，可能有坑；干完了还要按它的格式交差。玩过之后你会直观理解：为什么多智能体系统经常跑偏、死循环、做出来的东西不是用户想要的——因为任务在层层传递中被误解了。作者把这个日常抽象成游戏机制，HN 上 357 分说明这种"共情式教学"击中了很多正在开发 Agent 系统的开发者。

### 这跟普通人有什么关系

现在很多产品都在宣传"AI 员工团队"，但用户经常遇到 AI 干一半跑偏、反复确认、答非所问。这个游戏解释了根源：任务拆解和上下文传递是难点。理解这一点，你在使用或采购 Agent 产品时就能更准确地判断问题出在哪一层。

## 为什么值得架构师关注

多智能体系统的失败大多不是模型能力问题，而是**编排协议问题**：任务描述的完备性、上下文的传递损耗、工具权限的边界、结果验收的标准。这个游戏用最低成本让团队成员内化这些失败模式，比读十篇论文直观。设计自己 Agent 架构时，可以对照游戏机制逐项检查：子任务是否自带验收标准？子智能体拿到的上下文是否自足？工具集是否匹配任务？权限是否最小化？

## 核心内容

- 游戏机制：玩家扮演子智能体，接受 LLM 主智能体派发的任务，在受限工具与上下文下完成任务。
- 项目开源：github.com/gulivan/worker755，可自行部署或改造为培训素材。
- HN 357 分/89 评论，讨论集中在多智能体编排的真实痛点与游戏机制的对应关系。
- 本质是一场"共情式"的 Agent 工程教学实验，把抽象的编排失败模式变成可体验的机制。

## 行动建议

让负责 Agent 系统的团队成员各玩一局，然后对照自己的编排器复盘：哪些跑偏案例对应游戏里的哪类失败？把高频失败模式写成编排器的验收清单。了解成本为零，收益在于团队对 Agent 设计达成共同语言。
