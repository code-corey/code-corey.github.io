# graphmemory: Bitemporal AI Memory System（graphmemory：六变量衰减的双时态 AI 记忆系统）

> 📅 2026-10-30 | 🏷️ 值得研究的仓库 | ⭐ 150（7天）
> 🔗 原文：https://github.com/gh9ko8y/graphmemory

## 是什么

graphmemory 是一个 Python 实现的 AI 记忆系统，特点是「双时态（bitemporal）」设计：每条记忆同时记录「事情发生的时间」和「被记住的时间」，配合六变量记忆衰减、时间分级召回、TTL 过期、去重和竞争性检索机制。存储栈为 Neo4j + PostgreSQL + Redis 三件套。仓库 2026-10-30 创建，已获 150 星，是本周 Agent 记忆赛道值得研读的参考实现。

## 🔍 小白解读

### 先说几个词

- **AI 记忆系统**：让 AI 助手能「记住」跨会话的信息——你的偏好、历史决策、上下文。没有它，AI 就像每天失忆一次的同事。
- **双时态（bitemporal）**：给每条数据盖两个时间戳——「事实发生时间」和「记录入库时间」。就像病历上既要写「何时发病」也要写「何时就诊记录」，两个时间线分开管理。
- **记忆衰减（decay）**：记忆像人脑一样随时间变淡，越久远、越少被引用的记忆权重越低。本项目用六个变量共同决定衰减速度，而不是简单的「一刀切过期」。
- **TTL 过期**：Time-To-Live，给记忆设保质期，到期自动失效清理。
- **竞争性检索（competitive retrieval）**：多条候选记忆「竞争上岗」，只有胜出的记忆进入 AI 的上下文，防止把上下文窗口塞爆。

### 这篇到底在说什么

打个比方：给 AI 配一个「会遗忘、会整理」的大脑，而不是一个只进不出的仓库。目前的 AI 记忆方案常见两类毛病：要么全部堆着（越积越多，检索越来越慢越来越糊），要么简单按时间删（把还重要的老记忆误删）。graphmemory 的思路是模拟人类记忆的规律：每条记忆有六个变量参与衰减计算（记得越牢的忘得越慢），召回时按时间分级（最近的、相关的先上），过期有 TTL 兜底，入库前先去重，最后由竞争机制决定谁有资格进入 AI 当次的上下文。工程上它选了三个大家熟悉的存储组件分工协作：Neo4j 管关系图谱、PostgreSQL 管结构化状态、Redis 管热数据，是一份可以直接读代码学习的参考架构。上线几天 150 星，说明「记忆怎么管」确实是当前 Agent 开发者的普遍痛点。

### 这跟普通人有什么关系

你用的 AI 助手如果总是「记不住你上周说过什么」或者「翻旧账翻出一堆无关的东西」，背后就是记忆系统的设计问题。这类方案成熟后，AI 助手会更像「共事多年的老同事」：记得重点、忘掉噪音、不拿过期信息误导你。

## 为什么值得架构师关注

- **Agent 记忆层是当前生产化的最大缺口之一**：上下文窗口装不下长期协作历史，外挂记忆系统的「存什么、怎么衰减、怎么召回」缺成熟范式，本项目提供了一个完整的设计样本。
- **双时态设计有真实业务价值**：审计场景（「当时我们以为对的事实是什么」vs「后来更正的事实」）在金融、医疗等企业场景是硬需求，双时态是把这两个问题分开 answering 的标准做法。
- **成本与运维账要算清**：Neo4j + PostgreSQL + Redis 三件套意味着三份运维负担，中小团队应评估「砍到一两个存储」的简化路径，而不是照搬全家桶。

## 核心内容

- 双时态记忆模型：每条记忆同时携带事实时间与记录时间两条时间线（据仓库描述）。
- 六变量记忆衰减：衰减由六个变量共同决定，支持时间分级召回，而非简单过期。
- 生命周期治理：内置 TTL 过期与去重机制。
- 竞争性检索：候选记忆竞争进入上下文，控制上下文占用。
- 技术栈：Python 实现，Neo4j + PostgreSQL + Redis 组合存储；2026-10-30 创建，150 星。
