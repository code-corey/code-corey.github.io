# Building a Multi-Agent System from Scratch: Architecture Patterns（从零搭建多智能体系统：架构模式）

> 📅 2026-11-05 | 🏷️ 工程 & Agent | ⭐ HN 71分/27评论
> 🔗 原文：https://kadhar.dev/blog/multi-agent-systems-from-scratch

## 是什么
一篇从零讲起的多智能体系统架构博客：不用重型框架，直接用代码拆解多 Agent 系统的核心结构模式与各自权衡。HN 上获 71 分、27 条评论，在近期的多 Agent 话题中属于务实的工程向内容。

## 🔍 小白解读

### 先说几个词
- **多智能体系统（Multi-Agent System）**：让多个 AI 智能体分工协作完成一件事，像把一个大项目拆给几个专员，而不是让一个人从头干到尾。
- **编排者-执行者（Orchestrator-Worker）**：一个「项目经理」Agent 负责拆活、派活、收活，下面若干「专员」Agent 只管干活——最常见的多 Agent 骨架。
- **消息传递（Message Passing）**：Agent 之间不共享大脑，靠传递结构化消息沟通，就像同事之间靠邮件和工单协作而不是共脑。
- **状态管理（State Management）**：记录「任务现在进行到哪一步、谁在处理」，丢了状态，多 Agent 协作立刻变成乱哄哄的群聊。
- **失败处理（Failure Handling）**：某个 Agent 卡住或输出不合格时怎么办——重试、换人还是升级给人，决定了系统靠不靠谱。

### 这篇到底在说什么
打个比方：单体 Agent 像一个包揽一切的全能员工，能力上限就是他一个人的脑力；多 Agent 系统则是把公司拆成部门。这篇教程的价值在于它从「怎么拆」讲起：什么任务值得拆成多 Agent（通常是步骤多、可并行、每步工具不同的任务），拆完之后谁当调度、怎么通信、状态放哪、失败了谁兜底。文章强调这些模式并非新发明，而是把分布式系统几十年的老经验（消息、队列、幂等、超时）搬到 Agent 世界。对刚要上多 Agent 的团队来说，它回答的是「第一版架构该长什么样」而不是「要不要上」。

### 这跟普通人有什么关系
未来你用到的很多 AI 产品——自动客服、自动报表、自动运维——背后大概率都是多 Agent 协作。理解这套分工逻辑，就能明白为什么有的 AI 产品又快又稳、有的却答非所问：差别往往不在模型，而在架构。对小团队而言，先读懂模式再决定要不要引框架，能省下大量推倒重来的成本。

## 为什么值得架构师关注
多 Agent 是当前 Agent 平台建设分歧最大的地带：框架（LangGraph、CrewAI 类）与自研之间、单循环加工具与真多进程之间。这篇从零实现的教程提供了评估坐标系——如果团队连编排者-执行者的失败语义都讲不清楚，就不该上多 Agent；反之，文章中的状态与失败处理清单可直接抄成设计评审项。结合今天另一篇 skein（fail-closed 编排），可以看到社区正在把「安全失败」作为多 Agent 的一等公民设计目标。

## 核心内容
- 以「从零实现」的方式讲解多 Agent 系统核心架构模式：编排者-执行者分工、消息传递、状态与失败处理。
- 强调分布式系统的成熟经验（消息、超时、幂等）可直接迁移到 Agent 编排，无需从零发明。
- 隐含判断：多 Agent 不是默认选项——任务是否可拆分、可并行、可独立校验，是上多 Agent 的前置条件。
- HN 71 分/27 评论，社区反馈集中在其与主流框架方案的取舍讨论上（详见讨论区）。

## 行动建议
如果团队正处在「要不要拆多 Agent」的决策点：先用文章的模式清单给现有单体 Agent 做一次体检，列出单循环已无法满足的具体环节，再决定引入框架或自研。仅是技术储备需求则了解即可。
