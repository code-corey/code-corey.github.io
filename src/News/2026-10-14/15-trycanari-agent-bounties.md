# trycanari: Bug bounties for AI agents: canary-verified attacks, paid in shielded ZEC（trycanari：给 AI Agent 的漏洞赏金平台——金丝雀验证攻击，用 ZEC 隐私支付）

> 📅 2026-10-14 | 🏷️ Web3 & Crypto | ⭐ 6（新仓库，Web3×AI 交叉，问题独特入选观察项）
> 🔗 原文：https://github.com/aadityakumarsah/trycanari

## 是什么

trycanari 是一个本周新出现的开源项目（Python，2026-10-11 创建），瞄准一个此前几乎空白的交叉领域：给 AI Agent 发漏洞赏金（bug bounty）。它的两个设计点很有意思——用"金丝雀"机制验证攻击的真实性，用 Zcash 的屏蔽池（shielded ZEC）完成私密支付。星数尚低（6），但概念独特，作为 Web3×AI 方向的风向标入选观察项。

## 🔍 小白解读

### 先说几个词

- **漏洞赏金（Bug Bounty）**：厂商悬赏安全研究者找漏洞——找到了给钱。HackerOne、漏洞盒子都是这类平台。现在轮到"找 AI Agent 的漏洞"了。
- **金丝雀验证（Canary-verified）**：金丝雀源自矿工带金丝雀下井探毒气的传统，安全领域指"诱饵标记"——在系统里埋下独特的暗号，谁带着真暗号来报告，就证明谁真的打进来过。这能有效过滤"口说无凭"的假漏洞报告。
- **Zcash / 屏蔽池（Shielded Pool）**：Zcash 是以隐私著称的加密货币，其"屏蔽交易"连金额和双方都加密，外人看不到转账细节——适合"不想暴露收了哪家赏金"的支付场景。
- **Web3×AI 交叉**：用加密网络的支付、激励与验证机制，为 AI 生态提供基础设施。这里的应用是：Agent 时代的"捉虫有赏"。

### 这到底在说什么

企业部署的 AI Agent 越来越多，它们有权限、有钱包、能自主行动——自然也会成为被攻击的目标。传统漏洞赏金平台为人写代码的系统设计，而 Agent 的攻击面（提示注入、工具滥用、权限逃逸）形态不同。trycanari 想做的事是：让安全研究者攻击 AI Agent 的行为可以被客观验证——通过金丝雀标记确认"这次攻击真的成功了"，然后用 Zcash 的隐私支付把赏金发给研究者，双方的身份和金额都不过度暴露。为什么支付要隐私？因为安全研究者往往不愿意公开"我攻击过哪家公司"的履历，匿名赏金可以降低参与门槛。目前项目很早期（6 星），能不能活下来未知，但它指出的空白是真实的：Agent 安全的"众测市场"目前几乎不存在，而需求正在指数增长。

### 这跟普通人有什么关系

如果你会一点安全测试，这类平台未来可能是一份额外收入来源；如果你部署了 AI Agent，这类机制提示你：与其等出事，不如主动悬赏让人来"合法地攻击你"。

## 为什么值得架构师关注

- **Agent 安全的众测模式空白**：企业 Agent 上线前的安全验证目前主要靠内部红队；"可验证的第三方赏金"模式一旦成熟，会成为 Agent 上线流程的标准环节——值得提前关注其验证机制设计。
- **金丝雀机制可直接借鉴**：无论是否使用该平台，"在 Agent 系统中预埋可检测的诱饵标记（canary token）来发现提示注入与数据外泄"是即刻可落地的低成本防御。
- **加密支付在灰度协作中的角色**：隐私支付解决的是"研究者不愿暴露客户关系"的真实摩擦点，这类"激励设计×隐私"组合会在 Web3×AI 领域反复出现。
- **早期项目风险提示**：6 星、无审计、单作者，仅供观察学习，不建议生产依赖。

## 核心内容

- 仓库 aadityakumarsah/trycanari，Python，2026-10-11 创建，6 星——本期 Web3 仓库供给整体偏弱（多数低于质量线），该项目以问题独特性入选观察项。
- 定位：面向 AI Agent 的漏洞赏金平台，解决"Agent 时代缺众测市场"的空白。
- 机制一：canary（金丝雀）验证——用诱饵标记客观确认攻击成功，过滤无效报告。
- 机制二：以 Zcash 屏蔽池（shielded ZEC）支付赏金，保护研究者与委托方的隐私。
- 属于"链上智能体/加密原生 AI 应用"交叉方向的早期样本：验证、激励、支付三件套全部加密原生。
