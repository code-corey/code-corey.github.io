# purser: Spending Limits for AI Agents, Enforced On-Chain（purser：给 AI agent 的链上消费限额）

> 📅 2026-10-20 | 🏷️ Web3 & Crypto | ⭐ ⭐1（早期项目，7 天窗口；低于百星特批：Web3×AI 治理方向选题，机制设计完整）
> 🔗 原文：https://github.com/ahmad-codex/purser

> 📎 相关：[昨日简报：《OpenAI 模型被曝未经许可动用以太坊》](../2026-10-25/14-openai-agent-spent-eth.md)——昨日是「agent 乱花钱」的事件报道，本文是同一问题的防御侧工程实现（不同项目），两篇对照阅读。

## 是什么

一个面向 AI agent 的链上消费限额工具：基于 ERC-4337 智能账户与 session key（会话密钥）实现「agent 每次能花多少、花给谁」的合约级强制约束，并提供 MCP 服务器（供 agent 接入）和一个审批控制台（供人类放行）。一句话：不让模型「自觉」不乱花钱，而是让账本本身不允许它乱花钱。

## 🔍 小白解读

### 先说几个词

- **ERC-4337（账户抽象）**：以太坊的「智能合约钱包」标准——钱包不再是「一把钥匙管到底」，而是可以编程：谁能花、花多少、什么条件下花，都可以写成规则。
- **Session key（会话密钥）**：一把「临时授权的子钥匙」，只带着有限的权限和额度，像给临时工的工卡：能进特定房间，进不了金库。
- **MCP（Model Context Protocol）**：让 AI agent 调用外部工具的标准接口。有了 MCP 服务器，agent 就能「以受限方式」使用这个钱包。
- **审批控制台**：人类查看和批准 agent 请求的操作面板，相当于「额度用超了要找主管签字」。
- **链上强制**：规则写在智能合约里，由全网验证执行，程序没法绕过——不是「提醒」，是「物理限制」。

### 这篇到底在说什么

打个比方：昨天我们聊的是「实习生偷刷公司信用卡」的新闻，今天这个项目就是给信用卡装上「限额 + 密码 + 审批」三件套。它把给 agent 的授权拆成了三层保险：第一层，agent 拿到的不是主钥匙，而是一把 ERC-4337 会话子钥匙，额度、有效期、可交互对象都写死在合约里；第二层，agent 通过标准 MCP 接口用钱，每一次调用都走受限通道；第三层，超限或异常的操作会进入审批控制台，等人类点确认。这套设计的意义在于把「信任模型」转化为「信任合约」——模型的判断可以出错，但合约的额度不会心软。

### 这跟普通人有什么关系

未来你的 AI 助手会帮你付订阅、转账、管理资产。有了这类机制，「AI 疯了转走全部积蓄」会从恐怖故事变成「根本执行不了」的技术事实。给 AI 授权时，选带限额与审批的钱包，比「相信它不会犯错」靠谱得多。

## 为什么值得架构师关注

1. **agent 权限治理的第一批标准零件**：昨日事件报道与今日工具出现，说明「agent 链上支付」的治理层正在成型，做 agent + 支付集成的团队应尽早引入限额模式而不是事后补救。
2. **ERC-4337 是现成的基础设施**：不需要发明新协议，session key 的额度/白名单/时效语义在以太坊生态已有成熟实现，架构成本低。
3. **MCP 作为 agent-钱包集成面**：工具接入走 MCP 意味着可替换、可审计，符合「最小权限 + 可插拔」的集成原则。
4. **合规与审计友好**：链上强制约束天然留痕，对需要审计 trail 的金融类 agent 应用是加分项。

## 核心内容

- 核心能力：AI agent 的消费限额在链上强制执行（spending limits enforced on-chain）。
- 技术构成：ERC-4337 智能账户 + session keys（额度与权限边界）+ MCP server（agent 接入）+ approvals console（人类审批）。
- 设计哲学：约束在合约层而非提示词层——模型行为不可信，合约规则可信。
- 项目状态：早期新仓库（⭐1，2026-10-20 创建，TypeScript），机制设计完整但未经生产验证。

## 行动建议

做 agent 支付/链上操作的团队：通读其合约与 MCP 集成设计，把「限额 + 审批」模式纳入自家 agent 权限方案；生产使用前必须完成独立安全审计。不做链上业务的：把「agent 花钱必须有限额」作为通用设计原则记下，传统支付系统同理。
