# How the Claude Code team thinks about verification（Claude Code 团队如何思考验证）

> 📅 2026-11-17 | 🏷️ 工程 & Agent | ⭐ HN 256 分 / 199 评论
> 🔗 原文：https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/
> 💬 讨论：https://news.ycombinator.com/item?id=50529612

## 是什么

Claude Code 团队（作者 Addy Osmani）在官方工程博客首次系统披露其内部开发方法：团队约 90% 的代码由 Claude 编写与评审，支撑这个规模的核心机制是「验证循环」（verification loop）——让 agent 用端到端测试、属性测试、差分测试三类证据自查工作，并详解了如何保持「验证器本身诚实」。

## 🔍 小白解读

### 先说几个词

- **验证循环（verification loop）**：agent 干完活后，用测试和检查自动证明「活真的干对了」。好比工厂流水线末端的质检机，没有它，每件产品都得老板亲自看，产线开不了几台。
- **端到端测试**：模拟真实用户把整个功能从头跑一遍。相当于整车试驾，而不是只检查发动机。
- **属性测试（property test）**：不检查具体例子，而是检查「无论输入什么，某条规律必须成立」。比如「转账后总额不变」，机器自动生成千百种奇怪输入去试探。
- **差分测试（differential test）**：让新实现和旧实现跑同样的输入，对比结果是否一致。相当于新旧两个厨师各做一道菜，盲品对比。
- **rubric（评分量规）**：事先写好的打分标准清单。让一个独立的「评分员」照着清单给 agent 的产出打分，防止「自己夸自己」。

### 这篇到底在说什么

Claude Code 团队说了一个关键数字：他们团队 90% 的代码已经由 Claude 写、由 Claude 审。人怎么管得住这么多 AI 干活？答案是给每个 agent 配「自动质检」。没有质检时，你只敢同时开一两个 agent，因为每个的产出你都得亲眼看；有了可靠的验证循环，你可以同时开几十上百个，机器自动筛掉不合格的。他们还给出实验数据：在结构化文件生成任务上，加一个按量规打分的独立评分员，任务成功率比普通的提示词循环高出最多 10 分，而且越难的任务提升越大。文章把「值得投入的测试」收敛为三类——端到端、属性、差分——并强调现在让 agent 自己生成测试、基准和规格说明已经很便宜，生成之后它们就是软件，反复运行几乎不花 token。最后是闭环：agent 反复在某个检查上栽跟头（比如日志里泄漏用户数据），就把它固化成 hook 或写进 CLAUDE.md 规则，让同类问题基本不再发生。

### 这跟普通人有什么关系

如果你已经在用 AI 编程助手，这篇文章等于官方教你「怎么带 AI 徒弟」：与其盯着它干活，不如先建好验收标准（测试、检查清单），然后放手让它多线作业。对小团队来说，这是把一个人产能放大数倍的实操路径。

## 为什么值得架构师关注

- **并行度上限 = 验证能力**：agent 编排的吞吐上限不由模型智商决定，而由验证体系决定。「1-2 个 → 数百个」的杠杆点是把验证做成基础设施（可自动生成、可高频运行、失败可回写规则）。
- **质量数据可引用**：独立 grader + rubric 带来最多 +10 分任务成功率（最难任务增益最大），可直接作为内部引入「AI 评审岗」的立项依据。
- **成本模型**：测试与规格的生成成本已从「token 消耗」降级为「软件运行成本」，评审环节的单位经济性被重写，CI 流水线设计需要重新排布 agent 生成物。
- **防「验证器造假」**：文章专门讨论「keep verifiers honest」——验证器本身也是代码，也会被 agent 的投机行为钻空子，需要独立的评审机制对验证器做元验证。

## 核心内容

- Claude Code 团队**约 90% 的代码由 Claude 编写与评审**（官方博客，作者 Addy Osmani，2026-11-16 发布，11-17 登上 HN）
- 无验证循环时只能并行运行 1-2 个 agent；有验证循环可并行**数十到上百个**
- 内部实验：独立 grader 按 rubric 复核，结构化文件生成任务成功率**最高提升 10 分**，最难任务收益最大
- 三类最值得投入的测试：**端到端、属性（property）、差分（differential）**
- 测试、benchmark、规格说明可由 agent 低成本生成，生成后按软件方式高频运行，几乎不消耗额外 token
- 闭环机制：反复失败的模式固化为 hook 或 CLAUDE.md 规则（如检测日志中的用户数据泄漏），从源头阻止复发

## 行动建议

1. 量一下自己团队的「验证覆盖率」：agent 产出的代码有多少比例被自动化验证兜住——这就是你敢并行几个 agent 的天花板。
2. 试点「rubric + 独立评分 agent」：挑一类结构化产出（如 JSON 配置、迁移脚本）跑 A/B，验证 +10 分是否在你的场景复现。
3. 把高频失败的 agent 模式登记成 hook/规则资产，纳入团队仓库管理——这是新的工程负债形式，需要 owner 和评审流程。
