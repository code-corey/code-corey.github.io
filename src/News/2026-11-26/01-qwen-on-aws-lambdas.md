# Serving Qwen via AWS Lambdas for fun and 80x negative profit

> 📅 2026-11-25 | 🏷️ 工程 & Agent | ⭐ HN 128分/20评论
> 🔗 原文：https://noahbuilt.it/writing/qwen-on-5600-lambdas
> 💬 讨论：https://news.ycombinator.com/item?id=50638070

## 是什么

一位开发者写了一篇实战复盘：他把开源模型 Qwen 部署到 5600 个 AWS Lambda 函数上来提供推理服务，结果算下来是「80 倍负利润」——每赚 1 块钱要亏 80 块。这是一篇典型的 LLMOps 成本教育案例，属于「失败教训」类一手内容。

## 🔍 小白解读

### 先说几个词

- **Lambda / Serverless**：亚马逊云的一种「用完即走」的计算服务，你不用租一台一直开着的电脑，而是把代码丢上去，来一个请求它临时启动一个实例干活，按用量计费。好比摆摊：不用长期租店面，有人买东西才支摊。
- **LLM 推理**：让训练好的大模型回答问题的过程。训练像「上学」，推理像「上岗干活」，上岗是持续发生、真金白银花钱的部分。
- **单位经济学（unit economics）**：每提供一次服务，收入减成本还剩多少。如果每单都亏钱，量越大亏越多——这叫负单位经济学。
- **冷启动**：Serverless 实例闲置一段时间后被回收，下次请求要重新初始化。对要加载几个 GB 权重文件的 LLM 来说，冷启动可能长达数十秒（这是 Serverless 方案的公认痛点，文中语境相关）。
- **GPU 利用率**：显卡干活时间的占比。LLM 推理成本能不能摊薄，关键看这块「贵重设备」是不是一直满负荷运转。

### 这篇到底在说什么

打个比方：这就像有人开了家奶茶店，但没有买一台制冰机，而是每次顾客点单都临时去租一台制冰机、用完再还。每一杯奶茶的「设备租赁费」远超奶茶售价——卖得越多亏得越狠。作者正是用 5600 个 Lambda 这种「临时工」模式去跑大模型推理，最后算账发现收入只够成本的 1/80。这背后是 LLM 推理的公认特性：模型权重文件巨大，加载慢、占内存多，最适合的方式是「雇一个全职员工」（常驻 GPU 服务器）让它一直满负荷干活，而不是「来一单雇一次临时工」。作者把这笔账公开算给大家看，HN 上 128 分、20 条评论，社区讨论集中在自托管大模型到底该怎么算成本。

### 这跟普通人有什么关系

如果你是小公司想「自建 AI 服务」，这篇文章是一张免费的避坑图：别被「按用量付费=省钱」的营销话术带走，大模型推理恰恰是按用量付费最贵的场景。对普通打工人，它解释了为什么很多 AI 功能按月收费而不是按次收费——厂商也是被成本结构逼的。

## 为什么值得架构师关注

- **选型直接相关**：这是「Serverless 跑 LLM」路线的实证反例，80 倍负利润给出了量级感受，可作为自托管 vs 采购 API 决策时的引用数据点。
- **成本模型设计**：LLM 推理成本的关键变量（权重加载、显存带宽、GPU 利用率、批量大小）在函数计算架构下全部恶化，规划推理服务时应默认排除纯 Serverless 承载。
- **架构边界判断**：无状态、短生命周期、突发流量的 Serverless 与长驻、重状态、需批量合并的推理负载天然错配——这例子可写进内部架构评审的反模式清单。
