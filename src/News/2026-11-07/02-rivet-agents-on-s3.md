# Launch HN: Rivet (YC W23) – Scale and Orchestrate Agents on S3（用 S3 编排 Agent：不建库不搭队列）

> 📅 2026-11-05 | 🏷️ 工程 & Agent | ⭐ HN 118 分/58 评论
> 🔗 原文：https://github.com/rivet-dev/rivet
> 💬 HN 讨论：https://news.ycombinator.com/item?id=50381687

## 是什么

YC W23 批次公司 Rivet 在 Hacker News 上发布（Launch HN）其开源项目：一个把 Agent 的运行、编排和扩展构建在 S3 对象存储之上的框架。核心卖点是：不引入数据库、不引入消息队列，直接利用 S3 的持久性、无限扩容和强一致语义来承载 Agent 的状态与任务流转，仓库为 rivet-dev/rivet。

## 🔍 小白解读

### 先说几个词

- **Agent 编排（Orchestration）**：让 AI 助手按步骤干活时，谁来记「干到哪一步了」、谁负责「下一步该谁上」。打个比方：剧组里的场记和执行导演，演员（Agent）只管演戏，进度和调度归他们管。
- **S3 / 对象存储**：云厂商提供的「超大网盘」，按对象存文件，几乎无限量、按用量计费、跨机房冗余。AWS S3 是鼻祖，各家云都有兼容产品。
- **消息队列**：专门用来「排队派活」的中间件（如 Kafka、SQS），传统分布式系统的标配组件，但需要额外部署和运维。
- **持久化执行（Durable Execution）**：程序跑到一半崩了，重启后能从断点继续，而不是从头再来。长任务 Agent 特别需要。
- **Launch HN**：创业公司在 Hacker News 上的官方发布帖，创始团队会在评论区答疑。

### 这篇到底在说什么

现在要做「能长期自己干活」的 AI Agent，团队通常要搭一套很重的底座：数据库存状态、消息队列派任务、各种中间件保证不丢活。Rivet 的思路是反着来：这些事情 S3 一个就够了。S3 天然持久（写进去就很难丢）、天然可以存超大对象、天然按量计费，把它当成 Agent 的「工作台账」——每个 Agent 的状态、每一步的中间结果都写成对象，任务流转也通过对对象的读写来完成。这样开发者不需要运维任何额外基础设施，存储层随着用量自动扩展，成本模型也变得非常简单：存了多少、读了多少就付多少钱。这个项目和 Rivet 一起发布在 HN 上，118 分/58 评论，讨论区主要围绕「S3 能不能撑住高并发一致性」展开。

### 这跟普通人有什么关系

对普通开发者来说，这类「用最笨的存储干最聪明的事」的项目意味着：你不需要一套昂贵的分布式系统知识储备，也能让 Agent 稳定跑长任务。对小公司来说，少一套中间件就少一份运维工资和一份故障面。

## 为什么值得架构师关注

- **基础设施减法**：Agent 平台选型中出现了一条新路线——「对象存储即运行时」，直接砍掉 DB + MQ 两个高运维成本组件，对成本模型和故障域都是显著简化。
- **一致性边界要算清楚**：S3 的强一致读（read-after-write）虽已保证单对象一致，但跨对象的状态机正确性、热 key（同一 Agent 高频写）吞吐是评审重点，HN 讨论区集中质疑于此。
- **云锁定与可移植性**：基于 S3 API 意味着可跑在任何兼容对象存储（MinIO、R2、OSS）上，多云迁移成本低于绑定专有队列服务的方案。
- **与同期方案对照**：和 Temporal/Celery 这类「数据库 + 队列」派编排相比，S3 派牺牲部分低延迟换取零运维，适合长周期、大规模、对延迟不敏感的 Agent 批处理。

## 核心内容

- 项目定位：开源（GitHub rivet-dev/rivet），YC W23 公司 Rivet 出品，主打「Scale and Orchestrate Agents on S3」。
- 架构主张：Agent 状态、任务队列、持久化执行全部构建在 S3 对象存储上，不依赖额外数据库和消息队列。
- 发布形式：Launch HN 官方发布，团队在评论区直接答疑。
- 社区信号：HN 118 分/58 评论（发布约 48 小时内）。
- 背景：Rivet 此前以游戏服务器编排基础设施为人所知，此次明确转向 Agent 基础设施赛道（以仓库当前描述为准）。

## 行动建议

- 正在为 Agent 平台选型的团队，可把 Rivet 与 Temporal、Inngest 等做一轮对比 PoC，重点压测：单 Agent 高频状态写入、万级并发 Agent、故障恢复时间。
- 存量系统若已有 Kafka/DB 团队，不必为省组件而迁移；若是从零搭建且任务偏长周期批处理，S3 路线的运维成本优势值得认真评估。
- 阅读源码时重点关注其断点恢复与并发写冲突的处理方式，这是所有对象存储运行时方案的通用难点。
