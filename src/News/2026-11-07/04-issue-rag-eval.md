# zaxiu88888/issue-rag: RAG over GitHub issues with rigorous eval（带裁判审计与置信区间的 RAG 标杆范例）

> 📅 2026-11-07 | 🏷️ 值得研究的仓库 | ⭐ 104 星（7 天爆发窗口，创建于 2026-11-01）
> 🔗 原文：https://github.com/zaxiu88888/issue-rag

## 是什么

一个开源的「RAG over GitHub Issues」项目：用检索增强生成的方式在海量 issue（缺陷报告、功能讨论）中找答案。它的价值不在检索本身，而在评测方法论——项目自带一套人工校对过的评测集，先审计「裁判模型」（用来给检索结果打分的 LLM）自身是否可靠，汇报效果时只给置信区间、不给单点最优数字。创建一周收获 104 星，Python 实现。

## 🔍 小白解读

### 先说几个词

- **RAG（检索增强生成）**：让 AI 先去资料库里查资料，再基于查到的内容回答问题。打个比方：开卷考试，先翻书再作答，比硬背（纯靠模型记忆）靠谱。
- **评测集（Eval Set）**：一组提前准备好标准答案的考题，用来衡量 AI 系统好不好。考题本身出错了，成绩单就没有意义。
- **裁判模型（LLM Judge）**：用一个 AI 给另一个 AI 的答案打分。但裁判自己也可能偏心、也可能判错。
- **裁判审计（Judge Audit）**：先验证「裁判」打分准不准——比如对比裁判分数和人工分数的一致性。相当于先考核质检员，再让他考核工人。
- **置信区间**：不说「准确率是 87%」，而说「准确率在 83%–90% 之间」。承认测量有误差，比拍一个漂亮数字诚实。

### 这篇到底在说什么

很多团队做 RAG 项目的痛点不是「检索不出来」，而是「不知道自己做得好不好」：评测题是模型顺口编的、打分靠另一个模型拍脑袋、汇报时挑最好看的一次跑分。issue-rag 把这三件事全部反着做：评测集由人工逐条校对；上线裁判之前先审计裁判（测它与人工判断的一致性）；最后报告成绩时给出区间而不是一个孤零零的最高分。项目场景选的是 GitHub Issues 检索——这是开发者天天遇到、又很难检索好的真实语料（半结构化、口语化、互相引用）。一周 104 星不算爆款，但它的工程习惯在「人人都在刷分」的环境里显得稀缺，这正是它上榜的理由。

### 这跟普通人有什么关系

只要你用过公司内部的「智能客服」「文档问答」，就体会过它一本正经胡说的时刻。这类系统变得可信，靠的正是 issue-rag 演示的这套笨功夫：认真出考题、认真考核阅卷人、诚实报分数。

## 为什么值得架构师关注

- **可直接抄的评测流程**：人工校对评测集 → 裁判一致性审计 → 区间化报告，三步可以直接移植到任何内部 RAG 项目的验收标准里。
- **成本/可靠性权衡的实证素材**：GitHub Issues 属于脏语料，其结论比干净语料上的 benchmark 更接近生产环境真实表现。
- **组织流程含义**：区间化报告会改变对「效果提升」的沟通方式——小于区间宽度的提升应视为噪声，避免为 0.5% 的波动投入工程资源。
- **与同日 LLM 裁判级联案例（Hightouch）呼应**：裁判审计是级联架构的地基，两者组合成一套完整的「裁判工程」实践。

## 核心内容

- 仓库：zaxiu88888/issue-rag，Python，创建于 2026-11-01，一周约 104 星（7 天爆发窗口）。
- 功能：对 GitHub Issues 做检索增强问答。
- 方法论亮点一：自带人工校对（hand-reviewed）的评测集，不依赖模型自动生成的考题。
- 方法论亮点二：对裁判模型自身做审计（audit of the judge itself），先验证裁判再使用裁判。
- 方法论亮点三：汇报指标报告置信区间（interval），明确声明测量不确定性，而非只报最优数字。

## 行动建议

- 把「裁判审计 + 区间化报告」写进团队 RAG 项目的验收模板，两个动作的成本很低、收益立竿见影。
- 用它作为参照物检查自家评测集：如果考题是 LLM 生成的且从未人工过目，当前所有效果数字都要打折扣。
- 仓库尚新、星数刚过 100，建议以「抄方法论」为主、「直接引入代码」为辅。
