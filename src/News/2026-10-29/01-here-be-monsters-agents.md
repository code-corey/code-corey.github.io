# Here be monsters: What do you still need to know when agents do the work?（当 Agent 接管工作，你还需要知道什么）

> 📅 2026-10-27 | 🏷️ 工程 & Agent | ⭐ HN 196分/102评论
> 🔗 原文：https://blog.adrq.dev/here-be-monsters-what-do-you-still-need-to-know-when-agents-do-the-work

## 是什么

一篇发表于个人技术博客的工程实践文章，核心问题是：当 AI Agent 开始替你完成实际工作（写代码、改系统、跑流程）之后，工程师还必须亲自掌握哪些知识和技能。文章在 Hacker News 上拿到 196 分、102 条评论，说明它精准踩中了当前行业的集体焦虑。

## 🔍 小白解读

### 先说几个词

- **AI Agent（智能体）**：不只是"你问它答"的聊天机器人，而是能自己拆任务、调用工具、连续干活的 AI。打个比方：聊天机器人像电话客服，Agent 像你雇的一个实习生，你给目标，它自己跑腿。
- **Harness（执行框架/挽具）**：包在模型外面的那层"工作服"——提示词模板、可用工具、权限控制、执行循环。同一个模型套不同的 Harness，表现可以差很远，就像同一个员工给不同的岗位说明书。
- **验证（Verification）**：确认 Agent 干的活真的对，而不是"看起来对"。好比验收装修：不能因为师傅说"做好了"就签字，你得自己开关一遍水电。
- **技能退化（Skill Atrophy）**：长期把活全交给工具后，人自己的动手能力下降。就像有了导航之后，很多人不再认路。

### 这篇到底在说什么

打个比方：公司新来了一批非常能干的机器人实习生，活干得飞快，但它们偶尔会一本正经地犯错，而且犯错的方式是你没见过的。这篇文章讨论的就是：作为带这些"实习生"的工程师，哪些本事绝对不能丢。作者的观点（从标题与文章主旨看）是"地图上还有怪兽"——Agent 能完成大部分执行工作，但那些怪兽出没的地方（边界情况、安全边界、系统设计的隐性约束、错误的验收标准）仍然需要人亲自了解。也就是说，工程师的价值从"亲手写每一行代码"转向"知道该往哪看、看得懂对错、知道什么时候不该信 Agent"。HN 上 102 条评论的热烈争论也印证了这一点：大家吵的正是"如果不用亲手做，我们还算不算工程师"。

### 这跟普通人有什么关系

如果你是普通开发者或小团队负责人，这意味着你的岗位描述正在改写：从"产出代码的人"变成"验收产出的人"。会用 AI 只是入场券，能判断 AI 给的东西能不能上线，才是未来几年的核心竞争力。反过来，如果你完全不懂系统原理、只会复制粘贴 Agent 的输出，你就成了最容易被替代的环节。

## 为什么值得架构师关注

- **团队能力模型要改**：招聘与考核标准应从"代码产量"转向"设计与验收能力"，否则会养出一批"只会点确认按钮"的团队。
- **流程上必须补验收关卡**：Agent 产出的代码/配置进入主干前，需要比人工产出更强的自动化验证（测试覆盖、review 制度、灰度发布），因为人的审查精力是新的稀缺资源。
- **知识管理风险**：当经验不再通过"亲手做"沉淀在团队里，组织记忆会空心化——架构师需要刻意设计"人必须过手"的环节，避免关键系统无人真正理解。
- **成本结构变化**：人力成本下降的同时，验证与事故处理的隐性成本上升，ROI 计算方式要跟着变。

## 核心内容

- 文章主旨（基于标题与发表平台）：探讨 Agent 时代工程师仍需保留的知识与判断力，警告"全托管"思维的风险。
- HN 196 分、102 条评论，是当期关于"Agent 与工程师角色"讨论热度最高的话题之一，说明该问题已成为行业普遍焦虑而非个例。
- 发表于 adrq.dev 个人技术博客，属于一线工程师的一手实践视角，非厂商软文。
- 与当天 HN 另一篇高赞《AI promised less work. I've never worked more》（663 分）形成呼应：AI 提高效率的同时，人的工作重心在转移而非消失。

## 行动建议

- 对自己：把日常工作刻意分成"必须亲手过手"（架构决策、安全设计、生产变更）与"可委托 Agent"（样板代码、重复劳动）两栏，防止技能退化。
- 对团队：在 CI/CD 与 code review 流程中为 Agent 产出设置独立的验收标准，不要与人工产出混用同一套宽松流程。
- 对管理者：更新团队技能矩阵，把"验证能力"作为明确的考核项。
