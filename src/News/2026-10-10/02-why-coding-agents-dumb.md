# Why are coding agents so dumb?（编码 Agent 为什么这么笨？）

> 📅 2026-10-09 | 🏷️ 工程 & Agent | ⭐ HN 74分/66评论
> 🔗 原文：https://mtlynch.io/why-are-coding-agents-so-dumb/ ｜ 💬 HN 讨论：https://news.ycombinator.com/item?id=50020947

## 是什么

独立开发者 Michael Lynch（mtlynch，开源项目 TinyPilot 作者）2026-10-09 发表的博文，复盘他两年来使用 Claude Code、Codex、OpenCode 等编码 agent 时反复碰到的失败模式，并给出他对"为什么 agent 追不上模型进步"的归因猜想。文章在 HN 拿下 74 分、66 条评论，是一场扎实的一线工程实践讨论。

## 🔍 小白解读

### 先说几个词

- **编码 Agent**：能直接在你的项目里改代码、跑命令的 AI 工具，比如 Claude Code、Codex。
- **模型（Model）**：底层的大语言模型，负责"动脑子"生成文字和代码。
- **任务管理**：把一个大活儿拆成小步骤、安排先后顺序的能力——文中吐槽 agent 这方面很弱。
- **沙箱**：给程序画的一个"围栏"，限制它只能碰指定的文件和网络，闯祸也闯不出围栏。

### 这篇到底在说什么

作者的核心论点是：**模型进步很快，但驱动模型的 agent 软件拖了后腿**——模型是大脑，agent 是身体，身体笨，再聪明的大脑也发挥不出来。他列了一串具体的槽点：agent 不懂并行，明明十个互不依赖的小任务却一个一个串行干，计算机最擅长的多任务全浪费了；agent 不会委派，5 万行代码里找个模式，也非要用最贵最慢的模型硬扫，从不想到"这活儿可以派给便宜模型"；agent 不了解自己，你问它自己的功能，它居然要上网搜，还不管搜到的说明配不配它的版本；agent 写的计划没法读，罗列一堆零散细节就叫"计划"，让人懒得审查，最后干脆放它直接写代码；agent 动不动就停下来问问题，作者睡前派了个长任务，回来发现 agent 两分钟后因为"git 分支叫什么名字"这种小事干等了一整晚。安全上他更不客气：agent 只有在能访问你全部文件时才可用，厂商的沙箱形同虚设，他自己写了个真沙箱才敢放心用。最后他给出归因猜想：这是委托-代理问题——定方向的高管离一线开发者太远，他们看的演示和跑分测的是模型，不是 agent。他也承认这个解释不算满意，文末还向读者征集更好的 agent 推荐。

### 这跟普通人有什么关系

如果你觉得"AI 写代码一会儿聪明一会儿犯傻"，这篇告诉你：犯傻的往往不是 AI 的脑子，而是指挥它的那套"身体"和用法。理解了这一点，你就知道该抱怨什么、该往哪个方向调整自己的用法。

## 为什么值得架构师关注

团队推广编码 agent 时，失败大多不是模型能力问题，而是任务设计与验证环境问题：任务粒度太大、没有可运行的验证闭环、人审材料（计划/diff）不可读、沙箱边界靠"礼貌请求"而非确定性机制。这篇的价值在于把失败模式按"agent 工程短板"逐条拆开，可对照自查。对选型的直接启示是：评估 agent 不应只看演示和基准分（它们测的是模型），而要在自己的仓库里测任务拆分、并行度、计划可读性和文件系统隔离；把大任务拆小、给 agent 可执行的测试闭环，往往比换更强的模型更能提升成功率。文中"真沙箱、确定性访问控制"的建议，也应写进团队的 agent 安全规范。

## 核心内容

- 模型与 agent 要分开评价：模型是大脑、agent 是身体，2025 年初作者预期半年后 agent 会追上模型，实际一直没追上。
- 典型失败模式：不会并行执行互不依赖的子任务、不会按任务难度在多个模型间委派、不了解自身功能要靠联网搜索、计划写得难读导致人审形同虚设、为琐碎决策干等用户。
- 安全短板：官方沙箱约束力弱，作者自建基于 OS 级安全原语的沙箱，把 agent 限制在仓库目录内，访问控制必须是确定性机制而非提示词建议。
- 作者给出的"底线清单"：自动拆任务并按成本/速度/正确性选模型、计划从高层抽象写到细节、默认单仓库只读/按会话授权、Execute 模式下 30 分钟无响应自主决策、支持任意模型供应商、开源。
- 归因猜想：AI 工具投入不足是委托-代理问题——决策者关注的演示与跑分测的是模型而非 agent，与一线开发者的日常痛点脱节。

## 行动建议

- 对照文中失败模式自查团队的 agent 使用规范：任务是否拆得够小、是否明确并行机会、人审材料是否可读。
- 把「agent 改完必须跑测试」写进流程，给 agent 建一个可重复执行的验证闭环，替代"看起来对了"的主观判断。
- 用 OS 级沙箱把 agent 的文件和网络访问限制在仓库范围内，不要依赖提示词式的"温柔请求"。
