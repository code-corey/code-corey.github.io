# Cross-request KV cache exposure in the GLM-5.3 Workers AI model (155 responses)（GLM-5.3 跨请求 KV 缓存泄漏：155 条响应）

> 📅 2026-10-26 | 🏷️ 安全 & 评测 | ⭐ HN 178 分/71 评论 · Cloudflare 官方复盘
> 🔗 原文：https://blog.cloudflare.com/kv-cache-exposure-remediation/

## 是什么

Cloudflare 发布官方复盘：其 Workers AI 推理平台上运行的 GLM-5.3 模型出现了**跨请求 KV 缓存暴露**问题——本应隔离在单个请求内的推理缓存内容发生了跨用户可见，共涉及 155 条响应。Cloudflare 已发布修复（remediation）说明，此事在 HN 获得 178 分、71 条评论。

## 🔍 小白解读

### 先说几个词

- **KV 缓存（KV Cache）**：大模型推理时的一项核心加速技术。模型读一段长文本很费算力，系统就把"读过的中间结果"（键值缓存）存下来复用——就像读过长书的人做的笔记，下次翻到同一章直接看笔记，不用重读。
- **前缀缓存复用**：很多请求的开头是相同的（同一个系统提示词、同一段文档），推理服务就把这段公共前缀的"笔记"在请求之间共享，省下大量算力——省的是钱，也是时间。
- **跨请求泄漏**：本该属于请求 A 的缓存内容，被请求 B 看到了。就像合租公寓里公用的冰箱，本该只放公共食物，结果你的私人便当被室友翻了。
- **多租户（multi-tenant）**：一台基础设施同时服务众多互不相识的客户。隔离（isolation）是它的生命线——任何隔离失效都是重大事故。
- **推理基础设施**：跑大模型推理的服务器集群与调度系统，是所有 LLM API 背后的共享底座。

### 这篇到底在说什么

打个比方：LLM 推理服务为了省钱提速，发明了一个聪明的办法——把"读过的资料笔记"缓存起来，遇到读同样资料的其他用户，直接复用笔记。问题在于：这本笔记的页码管理出了 bug，导致一位用户翻到了另一位用户的笔记内容。Cloudflare 这次的事故就是这类问题：GLM-5.3 在 Workers AI 上的缓存隔离失效，155 条本应私密的响应内容发生了跨请求暴露。值得肯定的是 Cloudflare 的处理方式——发布完整复盘与修复说明（这正是安全社区倡导的 transparent remediation），HN 上 178 分的讨论热度也说明业界对此高度敏感：因为**几乎所有主流推理服务商都在使用 KV 缓存复用来压成本**，这次的 GLM-5.3 事故相当于给全行业敲了警钟——推理基础设施的缓存隔离，正在成为 AI 时代新的数据安全战场。

### 这跟普通人有什么关系

你在任何 AI 服务里输入的隐私内容（合同、代码、病历描述），理论上都可能因为这类缓存 bug 泄给陌生用户。选用 AI 服务时，"厂商有没有缓存隔离的公开安全说明"应该成为考量因素之一。

## 为什么值得架构师关注

- **供应商审计新增检查项**：选型 LLM API 时必须确认厂商的跨请求缓存隔离机制与事故历史——"是否对敏感租户禁用跨请求前缀缓存"应写入问卷。
- **多租户架构自查**：自建推理服务（vLLM/SGLang 等均支持前缀缓存）需审计缓存 key 的租户维度设计，敏感业务建议按租户硬隔离缓存或直接关闭跨请求复用。
- **成本与安全的量化权衡**：前缀缓存可显著降低 TTFT 与单位成本，但隔离失效的代价是数据事故——金融/医疗类负载应明确"安全溢价可接受"的决策线。
- **事故响应模板**：Cloudflare 的透明复盘（影响范围量化到 155 条响应）可作为内部 LLM 服务安全事故披露流程的参照。

## 核心内容

- 事故：Workers AI 平台 GLM-5.3 模型发生跨请求 KV 缓存暴露，波及 155 条响应。
- 响应：Cloudflare 发布官方复盘与修复说明（remediation post），属于一手安全披露。
- 行业含义：KV/前缀缓存复用是主流推理平台的标配降本手段，隔离失效风险具有全行业普遍性。
- 社区信号：HN 178 分/71 评论，推理基础设施安全成为近期讨论焦点。

## 行动建议

1. 立即盘点：梳理团队使用的所有推理端点（自建 + API），确认各自的前缀缓存策略与租户隔离设计。
2. 对敏感业务（含用户隐私、商业机密的负载）评估关闭跨请求缓存复用的成本代价，必要时按租户分池。
3. 把"缓存隔离"加入 LLM 供应商安全评审清单与渗透测试用例，并要求厂商提供事故历史披露。
