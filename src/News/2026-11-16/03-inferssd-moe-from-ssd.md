# InferSSD：从 SSD 流式加载 MoE 专家，跑超内存的大模型（Run models larger than your RAM or VRAM）

> 📅 2026-11-16 | 🏷️ 值得研究的仓库 | ⭐ 1181⭐（30 天慢热发现，创建于 2026-10-22，C++）
> 🔗 原文：https://github.com/wici-ai/inferssd

## 是什么

InferSSD 是 WICI AI 开源的推理引擎，构建在 llama.cpp 之上，核心思路：MoE（混合专家）模型任意时刻只激活少量专家，于是把「未激活的专家权重」留在 SSD 上，用到时再流式读入内存/显存。这样 MacBook（48GB 统一内存）可以跑 DeepSeek-V4.1-Flash-1017（763B 总参/8-16B 激活），一台 8GB 内存 + 16GB 显存的 RTX 5060 Ti 机器可以跑 816B 总参的 Muse-Spark-Open。项目直接消费标准 GGUF 文件，提供浏览器聊天界面和 OpenAI 兼容 API。

## 🔍 小白解读

### 先说几个词

- **MoE（Mixture of Experts，混合专家）**：一个大模型里装着很多「专家小网络」，每个问题只唤醒少数几个来干活。打个比方：一家大公司有几千名专家，每个客户来访只需叫上三五个相关的，其他人不用到场。
- **GGUF**：llama.cpp 社区通用的模型文件格式，相当于「打包好的模型压缩包」，一个文件拿来就能跑。
- **KV cache**：模型对话时缓存的中间计算结果，用于加速后续生成，会占用大量内存。
- **流式加载（Streaming）**：数据不一次性全部装进内存，而是用到哪块读哪块。就像打游戏时地图不是全部载入，而是走到哪加载到哪。

### 这篇到底在说什么

大模型越来越大，但电脑内存装不下怎么办？InferSSD 的思路是利用 MoE 架构的特性「偷巧」：虽然模型总参数有几千亿，但每个词的生成只会用到其中很小一部分（比如 763B 里只有 8-16B 在干活）。于是它把不常用的「专家」权重留在 SSD 硬盘里，需要时才读取。这样一来，一台内存远小于模型体积的普通电脑，也能跑超大模型——慢一些，但能跑。项目基于成熟的 llama.cpp，兼容标准 GGUF 模型文件，还附上了在 MacBook Pro M5 Max、RTX 5060 Ti、RTX 5090、DGX Spark 四档硬件上的详细实测数据。它解决的痛点很具体：本地部署/隐私推理想要大模型能力，但买不起能装下 763B 的机器（那通常意味着几百 GB 显存）。

### 这跟普通人有什么关系

对想在自己电脑上跑大模型的普通玩家：如果你的机器内存不够装下某个开源大模型，这个项目提供了一条「加一块大 SSD 就能跑」的路，不用换整机。不过体验上会有取舍——从 SSD 读数据比从内存慢，对话速度会受影响，具体快多少要看 README 里的实测数据。

## 为什么值得架构师关注

- **成本模型变化**：为「本地/私有化推理」做容量规划时，SSD 带宽成为可用的新维度；对激活比例悬殊的 MoE 模型（如 763B/8-16B），「内存只放共享权重 + 活跃专家、冷专家落盘」可以显著降低单节点内存门槛，影响推理集群的成本测算。
- **与显存扩展方案对比**：和 experts-offload 到 CPU 内存、多卡张量并行等方案相比，SSD 流式是「慢但便宜」的档位，适合离线批处理、低并发助手场景；选型时需要按 token/s 要求分档。
- **依赖与风险**：项目绑定 llama.cpp 生态与 GGUF 格式，兼容性迁移成本低（标准文件即可用），但项目较新（2026-10-22 创建）、Windows 支持仍在进行中，生产引入前需验证自身模型的量化格式兼容性。

## 核心内容

- 支持 MoE 专家 SSD 流式加载 + 常规 RAM 推理两种模式，README 给出已测模型清单：DeepSeek-V4.1-Flash-1017（763B 总参/8-16B 激活，Q8_0）、Muse-Spark-Open（816B/42B）、Qwen3.6-35B-A3B（35B/3B）、Qwen3.8 Flash Next（177B/A3B）、Gemma4 E4B（7.46B，普通模式）。
- 平台覆盖 macOS/Metal、Linux/CUDA，Windows 在开发中；Apache-2.0 许可证。
- 内存预算检查机制：加载前校验权重、KV cache 与工作内存是否超物理内存预算，装不下直接拒绝启动，Apple Silicon 上把约 2.15 GiB 的嵌入表留在文件里按 token 读取。
- README 附四档硬件（M5 Max 48GB、RTX 5060 Ti 8GB+16GB、RTX 5090 32GB+32GB、DGX Spark 128GB）在 4K prompt/256 输出 token 标准下的 token/s 实测，并与原生 llama.cpp 对比给出加速倍数。
- 提供 OpenAI 兼容 API 与浏览器聊天界面，可直接用社区已转换的 GGUF（mrfakename/Unsloth/Bartowski/Google 官方 QAT 等发布源）。

## 行动建议

值得评估试用：如果你的私有化部署场景受限于内存/显存容量而非延迟（如夜间批处理、内部知识库问答），下载对应模型 GGUF 按官方 benchmark 矩阵跑一轮自己的负载测试，重点核对「你的模型量化格式是否在支持列表 + SSD 顺序读带宽是否达标」。高并发在线服务场景暂不建议替换主力推理引擎。
