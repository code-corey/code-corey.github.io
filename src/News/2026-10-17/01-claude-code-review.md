# How the Claude Code team does code review（Claude Code 团队如何做代码评审）

> 📅 2026-10-16 | 🏷️ 工程 & Agent | ⭐ HN 210 分 / 196 评论
> 🔗 原文：https://claude.dev/blog/solving-code-review-at-anthropic/

## 是什么

Anthropic 的 Claude Code 团队在官方博客（claude.dev）发布文章，公开他们自己团队如何做代码评审。卖铲子的人先展示自己怎么挖矿——这是一个重度使用 AI 编码智能体的团队，把自己的评审流程、踩过的坑和解法摊开来讲的一手材料。

## 🔍 小白解读

### 先说几个词

- **代码评审（Code Review）**：别人写完代码，由另一个人检查把关再合并，就像出版社的校对环节，是软件质量的最后一道人工闸门。
- **Claude Code**：Anthropic 出品的编码智能体工具，能读懂整个代码仓库、自己规划改动、写文件、跑测试，像一个住在终端里的 AI 程序员。
- **PR（Pull Request）**：把一段改动提交给团队审核的"申请单"，评审就发生在 PR 上。
- **评审瓶颈**：当 AI 让写代码的速度翻了几倍，而"看代码的人"还是那些，队列就会越排越长——就像收费站只开了一个人工窗口。

### 这篇到底在说什么

打个比方：以前一个程序员一天写 500 行代码，评审他的人一天也看得完；现在 AI 一小时能生成 5000 行，评审的人就淹死了。Anthropic 的 Claude Code 团队自己就处在这种"洪水状态"里，于是他们把评审流程整个重做了一遍——哪些检查交给 AI 先过一遍、哪些必须人来看、评审的标准怎么定、工具链怎么配合。这篇文章就是他们把这套路数公开分享。有意思的是，他们既是编码智能体的开发者，又是编码智能体最重度的用户，等于在自家后院做实验。对所有正在"AI 写码、人来看"的团队来说，这相当于头部玩家公开了自己的作业。

### 这跟普通人有什么关系

如果你是普通开发者，你所在团队的 PR 队列大概率会因为 AI 而越来越长，评审方式迟早要变，这篇文章给了你一个可抄的模板。如果你是管理者，它回答了一个现实问题：人少了之后质量靠什么兜底。对小公司来说，用得起用不起专职评审，这套"AI 初审 + 人类终审"的思路都能裁剪着用。

## 为什么值得架构师关注

- **工程效能链路的咽喉**：引入编码智能体后，评审是吞吐量的决定性环节，选型时不看评审侧配套等于只买引擎不建加油站。
- **一手实践而非概念**：来自真实重度团队的流程设计，可直接对照自家 CI/CD 与评审门禁做差距分析，是评审侧工具（AI 初审、规则检查）选型的决策输入。
- **成本结构变化**：评审从纯人力成本变成"人力 + 推理调用"混合成本，预算模型要跟着改。

## 核心内容

- Anthropic 官方博客一手发布，主角是 Claude Code 团队自身的工程实践，非第三方转述。
- 核心命题：AI 编码智能体大幅提高代码产出速度后，代码评审成为新的工程瓶颈。
- 文章给出该团队重构评审流程的具体做法与经验教训（细节见原文）。
- HN 讨论 196 条评论，围绕"AI 评审的可信边界"与"人类评审还剩什么职责"展开，社区分歧本身就是选型参考。

## 行动建议

读原文，对照自己团队回答三个问题：PR 队列长度是否在 AI 引入后恶化？哪些评审项可以安全下放给 AI 初审？人类终审的检查清单是否需要重写？建议先在一个低风险服务上试点"AI 初审 + 抽样人审"，再决定是否全面推广。
